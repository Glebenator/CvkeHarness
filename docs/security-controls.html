01 / Operating model

Treat the model as a fallible operator

CvkeHarness does not center its safety model on a hypothetical model escape. It centers the failures that can damage an operator's systems: the wrong target, destructive side effects, scope expansion, stale state, duplicate mutation, exposed credentials, over-broad approvals, and unavailable recovery.

A profile is a named set of defaults over one canonical control catalog. An override changes one control without creating a second authorization system. Each new runtime session resolves the profile and overrides into an immutable effective policy with a short hash.

Deterministic facts first
Shell and tool calls are converted into effects such as read, create, overwrite, delete, privilege change, network access, or scheduled mutation.
Strictest effect wins
A compound action cannot hide a denied or approval-gated effect behind otherwise allowed reads.
Models advise, people authorize
An LLM review can add context for eligible actions, but a person is still required and the model cannot create reusable authority.
Advertisement is not permission
A tool can be visible to the model and still be stopped by the central registry policy at execution time.
Important boundary The current local shell backend is not an operating-system sandbox. CvkeHarness adds analysis, policy, approvals, binding, limits, redaction, and audit state. It does not claim kernel-enforced containment or automatic recovery.

02 / Decision pipeline

One policy path from proposal to execution

Authorization occurs immediately before a tool executes. Shell actions receive deeper syntax and target analysis, while other tools receive deterministic effect classification in the registry. Both paths resolve against the same immutable effective policy.

03 / Security profiles

Five starting points, every value still editable

Profiles select defaults. They are not separate execution engines. Changing a single value produces a profile with overrides, and applying another profile clears the old overrides only after confirmation.

Profile intent and practical consequences.
ProfileUse whenAutomatic behaviorPrimary interruption
Extra strictUnknown or destructive execution should usually stop.Known reads only. New files and append actions ask.Opaque scripts, deletes, overwrites, packages, remote changes, credentials, and devices are denied or gated.
Reasonable defaultYou want useful diagnostics with visible approval around consequential changes.Known reads, file creation, and append run automatically.Overwrite, delete, privilege, services, packages, network, remote, cloud, containers, databases, and scheduling ask. Credentials and devices are denied.
Less strictRoutine local and recoverable work should proceed with fewer interruptions.Most local mutations, packages, network, containers, and schedules run.Deletes, privilege, remote and cloud changes, destructive databases, and credentials still ask. Unknown actions receive advisory review plus human approval.
MinimalYou accept broad local autonomy but still want catastrophic-path and credential tripwires.Nearly every classified effect runs.Raw devices and credentials ask. Critical-path and credential-path protection remain enabled.
YOLOYou intentionally want CvkeHarness approval gates disabled.All catalog decisions allow, with maximum limits.No CvkeHarness interruption. OS permissions, cloud RBAC, provider locks, and database privileges still apply.
YOLO is not privilege escalation YOLO disables CvkeHarness approval and protected-path guards. It cannot elevate the current process, bypass operating-system permissions, remove cloud resource locks, or expand the credentials already available to the runtime.

05 / Configuration

Profile selection and typed overrides

The durable selection lives under security. Override values are strings so a missing value is distinct from an explicit false, allow, or numeric limit. Unknown profiles, unknown setting IDs, invalid decisions, and out-of-range limits fail validation.

security:
  version: 1
  profile: reasonable
  overrides:
    filesystem.delete: deny
    network.outbound: allow
    approval.reuse_this_session: "true"
    limits.timeout_seconds: "60"
  1. Load and normalizeOlder configuration is migrated only when the new security section is absent.
  2. ValidateThe schema version, profile, control IDs, decisions, booleans, and integer ranges must all be valid.
  3. ResolveThe selected bundle is copied, overrides are applied, each value receives an origin, and a policy hash is calculated.
  4. SnapshotA new runtime session receives an immutable policy. Saving Settings does not alter an active session.
Origin is visible The Settings editor shows whether each effective value comes from the profile or from an override. Applying a new profile asks for confirmation and clears the prior override map so old customizations do not silently follow the new bundle.

06 / Shell effect analysis

Classify consequences, not punctuation

The shell path first parses supported compound syntax, then classifies every segment and redirection. A greater-than sign is not a reason by itself to block a command. The destination, existence, stability, and resulting filesystem effect matter.

Redirection is converted into effects before policy resolution.
FormEffectReason
2>/dev/nullDescriptor plumbingNo persistent file mutation.
2>&1Descriptor plumbingRoutes one descriptor to another.
> new-filefilesystem.createThe resolved path does not exist.
> existing-filefilesystem.overwriteThe shell will truncate the existing target.
>> filefilesystem.appendData is appended to the target.
< fileRead, possibly credential accessSecret-bearing input paths add the credential effect.
> "$TARGET" or glob/brace targetUnknown plus write effectThe target is dynamic or unresolved, so it cannot inherit a safe create decision.

Supported compound syntax

Newlines, &&, ||, semicolons, and pipelines are segmented and assessed constituent by constituent. Quoted heredocs are supported as opaque scripts or data. The parser blocks constructs that would hide executable structure from the analyzer, including backticks, $(...), process substitution, unquoted heredocs, background &, and line continuation.

Executable identity

Known command names do not automatically make arbitrary binaries safe. A path-qualified executable outside trusted system directories is treated as unknown. A bare command resolved through PATH is also reviewed when it points outside /bin, /sbin, /usr/bin, or /usr/sbin. This prevents a local ./sort or shadowed ls from inheriting read-only authority by basename.

Target resolution and protected areas

Targets are normalized, existing symlinks are resolved, and non-existing paths bind through their resolved parent where possible. Wildcards, variables, command syntax, and braces make a target unstable. Critical-path protection escalates create, append, overwrite, delete, and relevant privilege changes for system roots, devices, repositories, backup or snapshot paths, and configured credential locations.

Covered mutation families

  • Filesystem commands such as rm, find write primaries, cp, mv, install, ln, tee, touch, truncate, sed -i, and dd.
  • Wrappers and interpreters such as sudo, env, xargs, shell -c, Python, Node, Ruby, Perl, and PowerShell.
  • Service, journal, package, raw-device, mount, network, SSH, Git, container, cloud, Kubernetes, Terraform, and database operations.
  • Deletion variants including git clean, rsync --delete, container prune, Kubernetes delete, HTTP DELETE, and destructive SQL.
Opaque scripts remain opaque A script file can contain effects that are not visible in the interpreter command line. Without an enforcement sandbox or typed adapter, opaque interpreter bodies add the unknown effect instead of relying only on commands.scripts.

07 / Non-shell tools

Registry authorization covers every effectful tool

The central registry authorizes tools when they execute, not when their definitions are advertised to a model. Known tools receive deterministic mappings. Future unclassified tools fall back to commands.unknown.

Cron has an additional state check Registry approval does not replace the crontab preview. The tool reads the current crontab, prepares the exact mutation, prints the diff, and requires confirmation immediately before applying it.

08 / Approval lifecycle

Approvals bind to what will execute

Old normalized command strings were too broad: they had no target, effect, policy, principal, directory, or expiry. Effect-policy runtimes quarantine those records. New approvals use an action digest and can be reused only within a deliberately narrow scope.

Grant bindings

  • Analyzer version and action kind.
  • Exact action payload digest and deterministic effect digest.
  • Effective policy hash.
  • Runtime hostname, local principal, and working directory.
  • Expiry and remaining use count.

Three approval scopes

How interactive, session, and deferred approvals differ.
ScopeLifetimePersistenceDrift behavior
Approve onceCurrent execution onlyNot reusableNo later reuse exists.
Approve and rememberCurrent process, only when the profile toggle is enabledMemory onlyDigest changes when target, effects, policy, host, principal, or directory changes.
Deferred grant15 minutes, one atomic useSQLite grant rowAny binding mismatch, expiry, or prior consumption stops execution.
Secret-bearing blocked work Blocked snapshots and continuation data are masked before persistence. If masking changes the exact action payload, the action cannot reconstruct the original digest and must be rerun interactively. Resume convenience does not override secret persistence boundaries.

09 / Setup and Settings

A recommended default with progressive customization

The Guided Console keeps profile choice on the critical path and moves the 25-control catalog behind explicit customization. The dashboard uses a dedicated Security subpage instead of extending the general Settings table indefinitely.

Guided setup

  1. Select a profileThe Safety stage presents Extra strict, Reasonable, Less strict, Minimal, and YOLO with consequence text. Reasonable is the default.
  2. Customize only when neededA reveals individual controls. Arrow keys or Space change values; R restores the selected profile value.
  3. Confirm broad posture changesYOLO requires a second explicit confirmation. Applying any new profile clears overrides only after confirmation.
  4. Review before saveReady shows the effective profile, override count, and policy hash. Saving configuration remains separate from installing dependencies or starting a daemon.

Dashboard Settings

  • The Security row opens a grouped control editor with effective value and source for every setting.
  • r resets one override. R asks before resetting all overrides. s saves.
  • Unsaved edits survive the dashboard's periodic refresh.
  • Saved changes apply to new chat sessions. The active chat keeps its immutable policy snapshot.
  • Overview and Chat show the effective profile summary and policy identity instead of only the deprecated safety mode.
Responsive and keyboard-first Setup and Settings are covered at 80, 100, and 120 columns. Status is explicit text, not color alone, and keyboard escape, confirmation, reset, and save paths remain visible.

10 / Persistence and privacy

Security state is private, bounded, and explicit

Durable data and its security treatment.
DataLocationProtection
Profile and overrides~/.cvkeharness/config.yamlValidated, atomic temp-file replace, mode 0600, deep-cloned before asynchronous use.
Scoped grantssecurity_action_grants in SQLiteDigest, scope, masked summary, expiry, and use count. No raw command is stored in the grant row.
Blocked workblocked_work in SQLiteSafe approval envelope plus masked conversation and continuation payloads.
Legacy command approvalscommand_approvals in SQLiteQuarantined from effect-policy runtimes and masked when listed.
State database~/.cvkeharness/state.db and SQLite sidecarsMode 0600. Grant consumption is one atomic conditional update with bounded lock retry.
Shell outputRuntime events and tool resultsBounded look-ahead, secret masking before visible truncation, then bounded emission.

Invariant protections are not profile toggles

  • Configuration validation and schema-version checking.
  • Private config, state, and authorization metadata permissions.
  • Secret masking at output and blocked-work persistence boundaries.
  • Bounded command size, segments, execution time, and captured output.
  • LLM review cannot persist permission or override deterministic denial.
  • Running sessions do not silently adopt a newly saved policy.

11 / Legacy migration

Old configuration remains readable without becoming a second authority

The new security section wins whenever it exists. Legacy values are consulted only when that section is absent, then projected back for transition compatibility.

Legacy safety_mode migration.
Legacy modeNew selectionCompatibility detail
llm_judgeReasonableAmbiguous actions follow the new catalog. Model review remains advisory.
user_confirmReasonable with create and append set to askPreserves the old expectation that a non-allowlisted file creation does not run automatically.
user_confirm_allExtra strict with every decision control set to askEvery valid effect remains human-reviewable instead of inheriting profile ALLOW or DENY values.
unrestrictedYOLOCvkeHarness approval gates are disabled, while external protections still apply.

Legacy capability preferences map Python scripts, autonomous diagnostics, network probes, and missing-tool installation into the corresponding script, read, network, and package controls. They no longer remain setup-only preferences with no runtime effect.

12 / Operator workflows

Inspect, approve, resume

cvkeharness commands list

Show the static allowlist, available or spent scoped grants, and quarantined legacy approvals. Grant summaries are masked.

cvkeharness commands approve "<command>"

Create one exact shell grant for the current policy, host, principal, and directory. It expires after 15 minutes and has one use.

cvkeharness commands approve-work <blocked-id>

Reconstruct the stored shell or non-shell action, reclassify it under the current policy, preserve the original executor scope, then issue one grant.

cvkeharness settings

Select a profile through the legacy terminal settings surface using the shared profile catalog.

cvkeharness setup

Run Guided Console onboarding with profile choice and progressive per-control customization.

Blocked work in Chat

When a TUI or background action reaches ask, the task becomes APPROVAL REQUIRED. Chat displays the blocked-work ID and the exact approve-work command. Approval resolves only the matching envelope; a changed policy or action requests fresh review.

13 / Validation evidence

Security semantics are tested, not only parsed

The implementation was reviewed against realistic bypasses after the initial green suite. Each discovered gap became a regression case, followed by fresh normal, race, vet, build, diff, and E2E runs.

14 / Limits and roadmap

What is not implemented yet

Controls appear in the product only when an enforcement mechanism exists. The following capabilities remain valuable follow-on work, not hidden or aspirational toggles.

Known limitations and recommended next enforcement layer.
Missing capabilityWhy it mattersRecommended direction
OS-enforced sandboxHeuristic classification cannot fully constrain opaque local code.Add filesystem, process, device, secret, and network enforcement with fail-closed availability checks.
Staging and recoveryApproval does not make deletion or overwrite reversible.Add Trash or managed quarantine, snapshot providers, backup-before-overwrite, recovery manifests, and restore verification.
Delete and write budgetsA classified action can still affect too many files or bytes.Enumerate operands and enforce file, byte, recursion, mount, and cumulative mutation limits.
Remote target fingerprintingLocal hostname and principal binding do not identify cloud accounts, clusters, databases, or SSH endpoints.Bind account, subscription, project, region, cluster, namespace, database, remote principal, and endpoint fingerprint.
Executable-content hashingA trusted path can change after analysis.Bind executable identity and content digest immediately before execution.
Typed mutation adaptersRaw shell cannot reliably expose provider preconditions, dry runs, idempotency, or recovery.Add plan/apply adapters for cloud, Kubernetes, services, packages, containers, and databases.
Tamper-evident auditPrivate local records are useful but not independent evidence.Add hash chaining or a separate append-only sink with provider operation IDs and postconditions.

15 / Research basis

Why the design focuses on effects and recovery

The implementation and roadmap follow a consistent lesson: model training and prompts help, but authorization must be enforced outside the model. Deterministic scope, constrained credentials, recovery, exact approvals, runtime boundaries, and verification reduce blast radius when the model is wrong.

  • YoloFS: A Safety-First Filesystem for AI AgentsMotivates staged filesystem effects, snapshots, progressive permissions, and reviewable hidden side effects. The paper analyzes a selected incident corpus, not a population incident rate.
  • AgentDojoDemonstrates both ordinary task failures and redirection through untrusted tool data.
  • GPT-5-Codex System CardDocuments layered coding-agent safeguards including sandbox boundaries, approvals, and monitoring.
  • Claude Code sandboxingShows a practical combination of filesystem and network boundaries with explicit permission crossings.
  • Sequential-harm monitoring studySupports treating monitor models as advisory because apparently benign steps can combine into harmful trajectories.
  • Amazon EC2 idempotencyIllustrates why ambiguous mutation outcomes need idempotency tokens and status reconciliation before retry.
  • Kubernetes API conceptsProvides concrete models for dry run, resource versions, and stale-write rejection in typed adapters.
