01 / Self-test

Choose your test route

Start with the temporary-file walkthrough. You will see CvkeHarness prepare a change, refuse a wrong approval, apply it, and restore the original with a fresh process. Then test the failure paths. Save Docker and VM testing for a second pass if you only have a short session.

Recommended order · time allowances are estimates, excluding downloads
RouteWhat you learnAllow
1. Manual files · steps 2–6Real CLI, exact approval, rollback, conflicts, protected paths, checked math. No provider or Docker required.20–30 min
2. Console + Docker · steps 7–8Agent approval plumbing, process death, low disk space, NGINX and remote batches.15–30 min
3. Real VM + full gate · steps 9–10SSH watchdog, genuine guest reboot and native Btrfs restore.20–40 min

Yes, you should test this yourself. The useful evidence is whether the actual file, service or guest returns to the expected state—even when the model or controller is gone. A success message alone is insufficient.

Keep the first experiment disposable. These steps use invented files and owned lab machines. Supported recovery adapters have specific limits; arbitrary shell commands are not automatically reversible. Do not substitute your real SSH configuration, credentials, database or home directory for a fixture.

Run the commands in your own terminal. This is a CLI/TUI project; GUI automation is not required. Automated tests compile CvkeHarness and call its actual CLI, and the Console test drives a real pseudo-terminal. The VM tests reach the guest through generated lab SSH keys.

02 / Self-test

Build an isolated practice copy

Open a terminal in your current checkout. Start a dedicated bash shell by typing bash; paste the following blocks there, in order. They require Go 1.26.2 or a compatible newer toolchain and Python 3. Keep this shell open so its variables remain available.

The build uses your existing Go dependency cache. The running app gets an empty temporary home, its own journal and one permitted target directory. No login or setup wizard is needed.

prepare workspace
set -euo pipefail
umask 077
cd /Users/coolcake/workspace/goProjects/CvkeHarness
go version
python3 --version

lab_repo="$PWD"
lab_dir=$(mktemp -d "${TMPDIR:-/tmp}/cvkeharness-selftest.XXXXXX")
lab_dir=$(cd "$lab_dir" && pwd -P)
lab_home="$lab_dir/home"
lab_target="$lab_dir/target"
lab_state="$lab_dir/journal/state.db"
lab_bin="$lab_dir/cvkeharness"
mkdir -p "$lab_home" "$lab_target" "$lab_dir/journal"
printf 'CvkeHarness self-test only\n' > "$lab_dir/SELFTEST"
go build -o "$lab_bin" .
printf 'Your practice directory: %s\n' "$lab_dir"

Define three small helpers. cvk always uses the practice home and state; json_field extracts an exact field; make_request writes valid JSON without hand-escaping paths.

define helpers
cvk() {
  HOME="$lab_home" "$lab_bin" recovery \
    --state "$lab_state" --root "$lab_target" "$@"
}
json_field() {
  python3 -c 'import json,sys; print(json.load(open(sys.argv[1]))[sys.argv[2]])' "$1" "$2"
}
make_request() {
  python3 - "$@" <<'PY'
import json, sys
change = {"action": sys.argv[1], "path": sys.argv[2]}
if change["action"] != "delete":
    change["content"] = sys.argv[3]
if change["action"] == "create":
    change["mode"] = 384  # 0600 in octal
print(json.dumps({"changes": [change]}))
PY
}
cvk identity
{
  printf 'set -euo pipefail\n'
  declare -p lab_repo lab_dir lab_home lab_target lab_state lab_bin
  declare -f cvk json_field make_request
} > "$lab_dir/session.sh"
printf 'To resume in a new Bash shell, run: source %q\n' "$lab_dir/session.sh"

Expected A compiled binary and JSON containing a target hash. All practice paths should resolve inside the printed directory. Canonical paths matter: macOS often maps /tmp to /private/tmp, which is why the setup uses pwd -P.

Save the printed source …/session.sh command; it restores these paths and helpers in a new Bash shell. If a positive step errors, stop that sequence and read the error. This dedicated shell uses set -e to avoid continuing with missing IDs or failed setup. Only explicitly marked refusal tests are expected to return an error. Starting step 2 again creates a new independent practice directory.

03 / Self-test

Change a file, then undo it

3A. Prepare and review

Create the original, save an independent reference, and prepare a replacement. Preparation captures backups; it should leave the target unchanged.

prepare change
printf 'enabled=false\n' > "$lab_target/settings.conf"
cp -p "$lab_target/settings.conf" "$lab_dir/original.conf"
make_request replace "$lab_target/settings.conf" $'enabled=true\n' \
  > "$lab_dir/change.json"
cvk prepare --request "$lab_dir/change.json" > "$lab_dir/plan.json"
lab_op=$(json_field "$lab_dir/plan.json" id)
lab_digest=$(json_field "$lab_dir/plan.json" digest)
cvk inspect "$lab_op"
cmp "$lab_dir/original.conf" "$lab_target/settings.conf"
test "$(json_field "$lab_dir/plan.json" status)" = ready

Expected status: ready, exactly one replace entry, and your practice path. cmp prints nothing when the bytes match. Review the request’s candidate text, the path, before/after hashes and the returned digest before continuing.

3B. Prove that a wrong approval is refused

refuse wrong digest
if cvk apply "$lab_op" --confirm wrong-digest > "$lab_dir/wrong-digest.log" 2>&1; then
  printf 'FAIL: wrong digest was accepted\n'
  exit 1
fi
cat "$lab_dir/wrong-digest.log"
cmp "$lab_dir/original.conf" "$lab_target/settings.conf"

Expected refusal An error saying the review digest or current policy does not match, and unchanged file contents. An unrelated error such as “command not found” is not a passing refusal.

3C. Apply the reviewed plan

Copying this next block authorizes the exact stored digest. Prepared plans expire after 15 minutes by default; if yours expired, prepare again and review the new plan.

apply change
cvk apply "$lab_op" --confirm "$lab_digest" > "$lab_dir/applied.json"
test "$(json_field "$lab_dir/applied.json" status)" = committed
cat "$lab_target/settings.conf"
printf 'enabled=true\n' | cmp - "$lab_target/settings.conf"
cvk inspect "$lab_op"

Expected committed, actual contents enabled=true, and capacity/verification evidence in the inspection output.

3D. Restore without a model or configured roots

Run a fresh CLI process with just the original journal path. Recovery remains tied to the recorded machine, user and manifest. No provider is initialized.

restore offline
HOME="$lab_home" "$lab_bin" recovery --state "$lab_state" \
  recover "$lab_op" --confirm "$lab_digest" > "$lab_dir/restored.json"
test "$(json_field "$lab_dir/restored.json" status)" = recovered
cmp "$lab_dir/original.conf" "$lab_target/settings.conf"
cat "$lab_target/settings.conf"

Expected recovered and byte-for-byte original contents, enabled=false. Keep the journal and its recovery/ directory together; they contain the recovery record and private artifacts.

04 / Self-test

Check conflicts and cancellation

Now simulate another program writing a file after CvkeHarness changes it. Recovery should preserve that newer edit and report failure. This is a different fixture so the successful example remains intact.

prepare conflict
printf 'original\n' > "$lab_target/conflict.conf"
make_request replace "$lab_target/conflict.conf" $'agent-change\n' \
  > "$lab_dir/conflict-request.json"
cvk prepare --request "$lab_dir/conflict-request.json" > "$lab_dir/conflict-plan.json"
lab_conflict_op=$(json_field "$lab_dir/conflict-plan.json" id)
lab_conflict_digest=$(json_field "$lab_dir/conflict-plan.json" digest)
cvk inspect "$lab_conflict_op"

Review the single conflict.conf replacement, then continue.

preserve conflicting writer
cvk apply "$lab_conflict_op" --confirm "$lab_conflict_digest" > "$lab_dir/conflict-applied.json"
printf 'human-change\n' > "$lab_target/conflict.conf"
if cvk recover "$lab_conflict_op" --confirm "$lab_conflict_digest" \
    > "$lab_dir/conflict-refusal.log" 2>&1; then
  printf 'FAIL: conflicting recovery unexpectedly succeeded\n'
  exit 1
fi
cat "$lab_dir/conflict-refusal.log"
printf 'human-change\n' | cmp - "$lab_target/conflict.conf"
cvk inspect "$lab_conflict_op"

Expected refusal recovery_failed, a restoration-conflict error, and human-change still on disk. Leave this example unresolved as evidence. Do not “fix” the test by forcing an overwrite.

Cancel a plan before it runs

A still-ready operation can be recovered as a verified cancellation. A delayed application of that same operation must then fail.

cancel ready plan
printf 'unchanged\n' > "$lab_target/cancel.conf"
make_request replace "$lab_target/cancel.conf" $'should-not-run\n' \
  > "$lab_dir/cancel-request.json"
cvk prepare --request "$lab_dir/cancel-request.json" > "$lab_dir/cancel-plan.json"
lab_cancel_op=$(json_field "$lab_dir/cancel-plan.json" id)
lab_cancel_digest=$(json_field "$lab_dir/cancel-plan.json" digest)
cvk inspect "$lab_cancel_op"

Review the plan, then authorize cancellation of that exact operation.

verify cancellation
cvk recover "$lab_cancel_op" --confirm "$lab_cancel_digest" > "$lab_dir/cancelled.json"
test "$(json_field "$lab_dir/cancelled.json" status)" = recovered
if cvk apply "$lab_cancel_op" --confirm "$lab_cancel_digest" \
    > "$lab_dir/cancel-refusal.log" 2>&1; then
  printf 'FAIL: cancelled plan was applied\n'
  exit 1
fi
cat "$lab_dir/cancel-refusal.log"
printf 'unchanged\n' | cmp - "$lab_target/cancel.conf"

Expected Cancellation records recovered; the later apply is refused because that operation is no longer ready. The file remains unchanged.

05 / Self-test

Test quarantine and protected files

5A. Delete a disposable file through the typed adapter

Here “delete” means quarantine on the same filesystem. It removes the visible file but retains recovery data; it does not reclaim disk space.

prepare quarantine
printf 'keep this original\n' > "$lab_target/delete-me.txt"
cp -p "$lab_target/delete-me.txt" "$lab_dir/delete-original.txt"
make_request delete "$lab_target/delete-me.txt" > "$lab_dir/delete-request.json"
cvk prepare --request "$lab_dir/delete-request.json" > "$lab_dir/delete-plan.json"
lab_delete_op=$(json_field "$lab_dir/delete-plan.json" id)
lab_delete_digest=$(json_field "$lab_dir/delete-plan.json" digest)
cvk inspect "$lab_delete_op"

Review the single delete entry and its quarantine location inside your practice target.

quarantine and restore
cvk apply "$lab_delete_op" --confirm "$lab_delete_digest" > "$lab_dir/deleted.json"
test "$(json_field "$lab_dir/deleted.json" status)" = committed
test ! -e "$lab_target/delete-me.txt"
cvk recover "$lab_delete_op" --confirm "$lab_delete_digest" > "$lab_dir/undeleted.json"
test "$(json_field "$lab_dir/undeleted.json" status)" = recovered
cmp "$lab_dir/delete-original.txt" "$lab_target/delete-me.txt"

Expected The file disappears after apply and returns with the original bytes after recovery.

5B. Try a synthetic sensitive path

This creates a fake .ssh directory inside the allowed practice root. It contains no credentials. Preparation should still refuse the protected path.

refuse protected path
mkdir "$lab_target/.ssh"
printf 'synthetic sentinel; not a key\n' > "$lab_target/.ssh/sentinel"
make_request delete "$lab_target/.ssh/sentinel" > "$lab_dir/protected-request.json"
if cvk prepare --request "$lab_dir/protected-request.json" \
    > "$lab_dir/protected-refusal.log" 2>&1; then
  printf 'FAIL: protected path was accepted\n'
  exit 1
fi
cat "$lab_dir/protected-refusal.log"
printf 'synthetic sentinel; not a key\n' | cmp - "$lab_target/.ssh/sentinel"

Expected refusal A protected-path error and unchanged sentinel. This is evidence about the typed recovery boundary. It does not prove that every arbitrary shell program is unable to touch a sensitive file.

06 / Self-test

Make the calculator catch a mistake

Check “75% of 8 GiB is 6000 MiB.” The correct result is 6144 MiB. The calculator uses exact rational arithmetic, explicit units and a requested rounding rule.

reject wrong math
cat > "$lab_dir/math.json" <<'JSON'
{
  "operation": "multiply",
  "left": {"value": "75", "unit": "%"},
  "right": {"value": "8", "unit": "GiB"},
  "output_unit": "MiB",
  "rounding": "exact",
  "expected": "6000"
}
JSON
if cvk calculate --request "$lab_dir/math.json" > "$lab_dir/math-refusal.log" 2>&1; then
  printf 'FAIL: incorrect expected result was accepted\n'
  exit 1
fi
cat "$lab_dir/math-refusal.log"

Expected refusal Computed result 6144 with a mismatch error. Then correct the expected value:

accept correct math
python3 - "$lab_dir/math.json" <<'PY'
import json, sys
path = sys.argv[1]
with open(path) as f:
    request = json.load(f)
request["expected"] = "6144"
with open(path, "w") as f:
    json.dump(request, f)
PY
cvk calculate --request "$lab_dir/math.json"

Expected Success with 6144 MiB. This verifies arithmetic, not that a real server has 8 GiB available. File and NGINX executors measure their targets independently. Case matters: GB and GiB are different units.

07 / Self-test

Verify the agent approval workflow

Run the automated Console journey from the same shell. The test starts its own local mock model endpoint, temporary home and actual Console in a pseudo-terminal. It approves a prepared operation once, verifies the persisted commit and file, shuts down the mock provider, and restores through the CLI.

test console
cd "$lab_repo"
go test -count=1 -tags=e2e ./e2e \
  -run '^TestRecoveryConsoleApprovalThenOfflineRestore$' -v \
  2>&1 | tee "$lab_dir/console-test.log"

Expected --- PASS: TestRecoveryConsoleApprovalThenOfflineRestore and final PASS. This validates product integration without paid model calls. It does not establish how reliably a live model chooses the tool, nor visually validate your native terminal.

For a later live-model trial, use a dedicated test account/configuration and only the disposable root. Ask the model to prepare a typed recovery_manage change, inspect the exact manifest, and approve once. Reject a proposed raw shell edit when evaluating recovery: that would exercise a different execution path. Keep the independent CLI restore available. Antigravity login is not required for any test in this guide.

08 / Self-test

Run the disposable Docker fault labs

Start Docker Desktop, then verify the selected context points at your intended local lab daemon. These commands create images, containers and an internal test network in that daemon. Image pulls and the image build need internet access; tests use generated fixtures and no model credentials.

check docker
cd "$lab_repo"
docker context show
docker context inspect
docker version
docker info
go env GOOS GOARCH

Check the Docker endpoint before continuing; a remote production context is the wrong target. For the complete route, use an ARM64 Go host and ARM64 Linux Docker daemon, as on this Apple Silicon setup. The current guest image/build is packaged for ARM64. An Intel/AMD64 host needs a separately validated VM image adaptation; the file and NGINX container tests can still be run with matching host/daemon architecture.

8A. Prepare the images

prepare images
docker pull alpine:latest
docker pull nginx:stable-alpine@sha256:dc5069ad14f19660b141b21236140b91656bf89bbc3e2417c70ae650cd66104c
bash scripts/build-recovery-vm.sh 2>&1 | tee "$lab_dir/image-build.log"
docker image inspect cvkeharness-recovery-vm:alpine323 \
  > "$lab_dir/vm-image.json"

The fleet test reuses the VM image’s SSH software even though that test does not boot a guest. The build context is only e2e/labvm/. The NGINX and Alpine VM base references are pinned; the file lab currently uses alpine:latest, and VM packages resolve when built. Save image IDs with results rather than assuming future rebuilds are identical.

8B. Run the container suites

test docker
bash scripts/test-recovery-docker.sh \
  2>&1 | tee "$lab_dir/docker-tests.log"
Look for these top-level tests and a final PASS
TestWhat should survive
TestRecoveryDockerFaultLab17 cases: process death across journal stages, partial writes, parent symlink swaps, actual full storage, bad math and conflicting restore.
TestRecoveryDockerNGINX11 cases: real NGINX health/reload, resource refusals, failed health rollback, interruptions, conflicting writers and dead master.
TestRecoveryDockerFleet11 cases: serial targets, dropped SSH acknowledgements, pinned identities, aggregate budgets, conflicts and durable repair limits.

File/NGINX containers have no external network. Fleet containers communicate on an owned internal network. None receive host mounts, a host Docker socket, host credentials or published ports. The fleet targets receive only the additional capabilities needed by the lab SSH daemon.

Fault-injection builds deliberately terminate child processes, sometimes with exit code 86. That is expected only where the enclosing test verifies the crash and restored state. A top-level FAIL, missing image or unavailable daemon is a failed test run, not evidence of recovery.

Run only file and NGINX tests

This excludes the fleet’s VM-image dependency. Pull Alpine and pinned NGINX first. Host and Docker architecture must match.

test two containers
go test -count=1 -tags=e2e,recoverydocker ./e2e \
  -run '^TestRecoveryDocker(FaultLab|NGINX)$' -v \
  2>&1 | tee "$lab_dir/file-nginx-tests.log"

09 / Self-test

Test real reboot and snapshot recovery

A Docker container shares its host kernel, so container restarts alone cannot establish boot recovery. This lab runs a QEMU Linux guest inside an owned container. The tests compare kernel boot IDs and use real ext4/Btrfs guest disks.

test vm
cd "$lab_repo"
bash scripts/test-recovery-vm.sh \
  2>&1 | tee "$lab_dir/vm-tests.log"
All three top-level VM tests must pass
TestEvidence
TestRecoveryVMKernelPersistenceAndOfflineRecoverySeparate guest kernel, journal survival across reboot, CLI restoration when normal configuration is unavailable.
TestRecoveryVMNativeSnapshotsReal Btrfs checkpoint/restore, crash recovery, conflicting tree refusal and retained displaced tree.
TestRecoveryVMSSHGuard13 cases: fresh-transport confirmation, client death, lost acknowledgement, watchdog restart, conflicting edits and guest reboot before confirmation.

The outer container is capped at 2 GiB and two CPUs; the guest uses 1 GiB and two virtual CPUs. Guest SSH forwards bind only inside the outer container’s loopback namespace. No host disk devices or host directories are passed through. The suite manages its own SSH daemon and disks—you do not need to change your Mac’s SSH service or run host disk-formatting commands.

Expected Final PASS, with the reboot/watchdog cases actually executed. Timed rollback tests intentionally wait; allow the suite to finish. An unavailable VM image must fail the explicit suite. A skipped or unrun VM route means boot/snapshot recovery is unverified on your setup.

Keep a complete result

Once individual routes pass, run the combined gate before trusting a release candidate. It runs the local suite, race detector, vet and all compiled CLI/PTY/Docker/VM tests. This repeats earlier checks intentionally; run it after your final code changes.

test full gate
cd "$lab_repo"
git rev-parse HEAD > "$lab_dir/revision.txt"
git status --short > "$lab_dir/working-tree.txt"
docker image ls --digests > "$lab_dir/image-inventory.txt"
bash scripts/test-recovery-all.sh \
  2>&1 | tee "$lab_dir/full-gate.log"
printf 'Full gate passed; evidence: %s\n' "$lab_dir"

set -o pipefail, enabled in step 2, prevents tee from hiding a failing test command. The final success line should appear only if the gate exits successfully. Record dirty working-tree status alongside the commit: a commit ID alone does not identify uncommitted code.

11 / Self-test

Handle failure and clean up

Choose the response that preserves evidence
SymptomNext step
Plan expired / policy changedFor an unapplied practice change, prepare again and review the new digest. Do not change global policy to make an old approval pass.
Apply interrupted / unknownInspect, then reconcile with the original state and ID. Independently read the target before deciding to recover. An error does not mean nothing changed.
Restore conflictPreserve the newer file and journal. In a real operation, resolve which version should win before deliberate operator recovery. Do not repeat automatic repairs indefinitely.
Protected path / symlink / metadata refusalUse the fresh canonical practice root and plain fixtures. Do not remove protection or strip metadata from real files to satisfy a demo.
Docker cannot connect / missing imageStart Docker, verify its local context, and finish image preparation. A pull failure is a setup failure. Keep your normal Docker credentials unchanged.
Exec format / guest will not bootCheck Go/daemon architecture and the ARM64 VM requirement. Container-only success is not VM evidence.
Socket “operation not permitted”The Console fixture requires a local HTTP listener and PTY. An agent sandbox may block these; rerun from your ordinary permitted development terminal and report the environment restriction separately.
Unexpected test failureRetain the named test, exact error, revision/status, image IDs and full log. Stop the release decision; do not count an unrelated refusal or manual cleanup as a pass.

Inspect an interrupted manual operation

If the shell closed, open a new bash shell and run the source …/session.sh command printed in step 2. The following reloads the original operation from step 3. For another operation, use its own saved plan/inspection; do not mix IDs and digests. Inspection and reconciliation do not restore files.

inspect interruption
lab_op=$(json_field "$lab_dir/plan.json" id)
lab_digest=$(json_field "$lab_dir/plan.json" digest)
cvk list
cvk inspect "$lab_op"
cvk reconcile "$lab_op"
cat "$lab_target/settings.conf"

After review, use the exact recover command from step 3D if restoration is appropriate. For an interrupted fleet batch, inspect/reconcile its recorded target outcomes; never redispatch an already-dispatched batch just because an acknowledgement was lost. Model recovery has a durable attempt limit; the deliberate operator CLI is the escape hatch after diagnosis.

Check for leftover lab resources

Normal test cleanup removes each test’s own containers and internal network. If a run was killed, list only recovery-labelled resources:

inspect lab cleanup
docker ps -a --filter label=cvkeharness.test=recovery
docker network ls --filter label=cvkeharness.test=recovery
printf 'Manual files and logs remain at: %s\n' "$lab_dir"

Before removing a leftover, verify its name, label and that no test is still using it. Remove only those exact container/network IDs through Docker Desktop or targeted Docker commands. Do not run a global prune. Cached test images can stay for the next run.

Keep the manual directory until you have inspected the intentional conflict and saved your logs. Then delete only that printed cvkeharness-selftest.… directory using your file manager. It includes the test binary, journal, quarantine and fake home. Never delete real recovery state while a real operation may need it. Type exit to leave the dedicated Bash shell.

12 / Self-test

Decide what the results justify

A full pass supports using these specific adapters on disposable, representative systems, then a small noncritical target with independent backups and an out-of-band recovery path. Start with one regular file and one target. Broaden only after its actual permissions, filesystem and service configuration match the supported boundary.

It does not establish universal machine rollback or public-release readiness by itself. Arbitrary shell effects, active database consistency, unsupported metadata, physical disk loss, live-model judgment and unrelated release concerns still need separate evaluation. A Btrfs snapshot is not an off-machine backup, and open file descriptors can still refer to the displaced tree after a restore.
