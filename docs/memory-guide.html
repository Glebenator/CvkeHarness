CvkeHarness / Memory / Operational memory

Operational memory

CvkeHarness uses target-scoped operational memory to provide concise historical context during planning. Memory does not grant permission to execute commands.

Audience: operators and maintainers · Persistence: SQLite · Scope: one target and environment

Safety invariant

Memory can influence what a model proposes. Managed policy and valid approvals determine what CvkeHarness can execute.

Overview

CvkeHarness stores four types of operational knowledge:

  • Facts: typed, low-risk observations obtained from explicit probes.
  • Playbooks: target-specific procedures with verification steps, actions, and explicit success checks.
  • Findings: reusable observations about one target and environment.
  • Cautions: short-lived warnings based on failures or denied approaches.

SQLite at the configured state_db_path is the canonical source for live target inventory and operational knowledge. Markdown files in the memory directory are generated views and validated import material.

What memory does not contain

Operational memory is not used to store:

  • managed policy or permission rules;
  • durable command approvals;
  • credentials, API tokens, private keys, or passwords;
  • host-to-environment mappings created only by a model;
  • verified outcomes inferred only from exit code zero.
Note

guidance.md is user-authored prompt context. It is not managed policy and cannot override shell validation or approval requirements.

Core concepts

CvkeHarness separates enforcement, identity, historical knowledge, and current execution state into four planes.

1 Managed policy

Safety mode, shell validation, diagnostic allowlist, deny rules, and approval gates. This plane controls execution and is not model-writable.

2 Live fleet inventory

Deterministic endpoint-label ID, environment, transport, operator-confirmed remote identity label, confirmation time, and expiry.

3 Operational knowledge

Facts, playbooks, findings, and cautions. These records are historical planning hints and pass read-time safety checks before retrieval.

4 Run state

The current task, tool outcomes, telemetry, verification result, and resumable blocked work. Run state is not durable operational truth by default.

Canonical persistence

Normal retrieval reads operational state from SQLite. If SQLite is unavailable, operational memory fails closed. CvkeHarness does not treat a populated Markdown file as a fallback authority.

Generated Markdown files are written using atomic file replacement. Operational state updates use one SQLite transaction. If view generation fails after a database commit, run cvkeharness memory export to regenerate the views.

Target and environment scoping

Every active remote target requires the following endpoint-label fields:

Field Description Example
target_id Opaque identifier derived from the endpoint labels known to CvkeHarness. target-7f31d4b8c0a1
environment Operational tier. Values such as production and staging are separate scopes. production
transport Connection mechanism. ssh
remote_identity Operator-confirmed transport-specific label. ops@api-01
expires_at Time after which the target binding is no longer considered live. RFC 3339 timestamp
Endpoint-label limitation

CvkeHarness does not validate a live machine fingerprint, SSH host-key fingerprint, or cloud instance identity. A target record scopes memory to operator-confirmed labels; it does not cryptographically prove which machine currently answers the endpoint. Verify the live endpoint before mutation.

Bind a provisional target

New remote targets begin with environment=unknown. After independently confirming the endpoint labels, bind its environment and remote identity once:

cvkeharness memory target set-environment \
  target-7f31d4b8c0a1 production ops@api-01
Ambiguous target

An already-bound target cannot be rebound. If a requested environment conflicts with the stored label, or one label matches multiple environments, CvkeHarness withholds target memory. An LLM judge cannot authorize a shell command when the target is unresolved or ambiguous.

Memory lifecycle

Model-authored knowledge and learned procedures enter the review inbox as untrusted candidates. They are not included in prompt retrieval before operator promotion.

candidate → operator review → active → expired or revoked

A candidate can instead become rejected. Lifecycle transitions are one-way:

  • only a candidate can be promoted or rejected;
  • only an active record can be revoked;
  • a rejected or revoked record cannot be reactivated with promote;
  • delete removes a record from canonical operational state.
Promotion is not verification

Promotion records operator trust and adds a bounded expiry. It does not create a verification timestamp. A playbook must contain a success check before promotion, and the retrieved procedure is still presented as a verify-first historical hint.

Read-time safety checks

Before a record is retrieved, CvkeHarness checks:

  1. the target binding is active and unexpired;
  2. the target ID and environment match exactly;
  3. the record status is active;
  4. trust is operator or verified;
  5. the record has not expired;
  6. the evidence hash matches the stored content;
  7. for playbooks, at least one explicit success check exists.

Candidate, rejected, revoked, expired, wrong-scope, untrusted, and integrity-invalid records are excluded.

Manage operational memory

Prerequisites

  • The configured SQLite state database must be available.
  • Before promotion, confirm the target ID and environment independently.
  • Do not place credentials or private material in notes, commands, or import files.

Inspect current memory

  1. Show the generated views and snapshot count. 
    cvkeharness memory show
  2. Review records under the headings for targets, playbooks, findings, and cautions.

Review and promote a candidate

  1. List candidates. 
    cvkeharness memory inbox
  2. For the candidate, inspect target, environment, source, trust, evidence reference, evidence hash, observed time, expiry, sensitivity result, and summary. Playbooks also show success checks.
  3. Confirm that the content is narrow, contains no sensitive data, and applies to the displayed target and environment.
  4. Promote the exact record. 
    cvkeharness memory promote finding finding-9

Reject a candidate

Reject content that is incorrect, too broad, sensitive, or not useful:

cvkeharness memory reject caution caution-17

Revoke active memory

Revocation immediately removes an active record from retrieval while leaving it available for inspection:

cvkeharness memory revoke playbook pb-42

Correct memory with export and import

  1. Export a review copy. 
    cvkeharness memory export ./memory-review
  2. Edit the Markdown files in ./memory-review.
  3. Import the edited copy. 
    cvkeharness memory import ./memory-review
  4. Inspect the resulting state. 
    cvkeharness memory show

Import validates target and environment scope, status, trust, expiry, playbook success checks, and known credential markers. If integrity-bound content changed, import records source=operator_import, assigns a validated import evidence reference, and recalculates the evidence hash. A validation rejection does not change canonical SQLite state. If a generated-view write fails after the database commit, the command returns an error but SQLite contains the imported state; run cvkeharness memory export to regenerate the views.

Delete a record

Delete removes one fact, playbook, finding, or caution from canonical operational state:

cvkeharness memory delete finding finding-9
Snapshot retention

Delete does not erase generated-view snapshots. Snapshots are retained as local audit history and can contain a previous version of the record. The current CLI does not provide a snapshot purge command.

Approvals and memory

Approvals are enforcement records. Operational memory is planning context. They are stored and evaluated separately.

Property Operational memory Reusable command approval
Purpose Provide historical context for planning. Allow one exact action through an approval gate.
Created by Explicit probes or operator review; probe results remain candidates. Explicit user action only.
Scope Target ID and environment. Interactive: exact session plus command, action, target, environment, remote identity, policy version, and expiry. CLI exception: the same scope without a session.
LLM effect May influence a proposal. An LLM judgment cannot create a reusable approval.

Create an explicit CLI policy exception

cvkeharness commands approve "systemctl restart api" \
  --target target-7f31d4b8c0a1 \
  --environment production \
  --ttl 1h

This command is an explicit operator policy exception, not an interactive remembered approval. It is intentionally session-independent, with a maximum TTL of 24 hours. Reuse is limited to a narrow set of target-level commands. Runtime interpolation, shell globbing, and path-dependent commands are excluded. The target binding must remain active, unexpired, and attached to the same remote identity label.

An interactive remembered approval is different: it is persisted only when an exact session ID exists and can be reused only by that same session. Missing-session and cross-session reuse fail closed.

approved_once decisions are not returned by reusable-approval queries. The default allowlist permits diagnostic systemctl actions such as status, is-active, and is-enabled. Mutating actions require an approval path.

Command reference

cvkeharness memory show

Show generated memory views and the snapshot count.

cvkeharness memory inbox

List candidate facts, playbooks, findings, and cautions with review metadata.

cvkeharness memory promote <kind> <id>

Promote one candidate to bounded active memory.

cvkeharness memory reject <kind> <id>

Reject one candidate.

cvkeharness memory revoke <kind> <id>

Revoke one active record.

cvkeharness memory delete <kind> <id>

Remove one record from canonical operational state. Snapshots remain.

cvkeharness memory export [directory]

Generate Markdown views from canonical SQLite state.

cvkeharness memory import [directory]

Validate Markdown and replace canonical operational state in one SQLite transaction.

cvkeharness memory target set-environment <target-id> <environment> <remote-identity>

Bind an environment=unknown provisional target once. Already-bound targets are rejected without mutation.

cvkeharness commands approve "<command>" --target <id> --environment <env> --ttl <duration>

Create an explicit, session-independent CLI policy exception with exact remaining scope.

Review IDs

For playbooks, findings, and cautions, use the record ID shown by memory inbox or memory show. Facts use target_id:key.

How DevOps memory differs from coding-agent memory

Coding-agent memory is commonly scoped to a repository, user, folder, or session. CvkeHarness operates across computers and environments, so its memory model adds fleet-specific controls.

Concern Typical coding-agent memory CvkeHarness DevOps memory
Primary risk Stale repository convention or an incorrect implementation hint. Wrong host, wrong environment, or excessive operational blast radius.
Identity boundary Repository, folder, user, or session. Deterministic endpoint-label ID, environment, transport, and operator-confirmed remote identity label; no live machine fingerprint.
Use before mutation Context may be applied directly inside a workspace sandbox. Verify the live target and current state, then evaluate managed policy and approval.
Permissions Often handled by the coding tool or workspace sandbox. Managed policy and short-lived approvals are separate from memory.
Production separation A branch or worktree is often the primary scope. Development, staging, and production remain distinct even when hostnames overlap.
Remote credentials Repository secret handling remains important. Credentials are excluded from operational memory and known secret markers are rejected during import.
Failure behavior Missing memory typically reduces convenience. Unavailable SQLite, ambiguous identity, expired evidence, or failed integrity checks withhold memory.
Before mutation

Confirm the live target, exact environment, current system state, and intended postcondition. Historical success is evidence, not authorization.

Security and privacy considerations

  • Model-authored notes and failed output remain candidate-only until review.
  • Known credential markers are redacted on selected write paths and rejected during validated import.
  • Commands containing likely secrets are not learned as playbooks or facts.
  • Evidence hashes detect content changes during normal retrieval.
  • Generated exports and snapshots can contain host identities, environment names, procedures, and failure history.
Protect exported files

Treat memory exports and snapshots as internal infrastructure documentation. Store them with access controls appropriate for system inventory and operational history.

Secret-marker detection is a defense-in-depth filter, not a complete data-loss-prevention system. Operators must still inspect candidates and import files for sensitive values that do not match known patterns.

Troubleshooting

A candidate does not appear in the agent prompt

This is expected. Candidates appear in cvkeharness memory inbox and are excluded from retrieval until promotion. Promotion also requires an exact, known target environment.

An active record stopped appearing

Check the live target status and expiry, exact environment, record status, trust, expiry, evidence hash, and playbook success checks. Any failed gate excludes the record.

Editing a generated Markdown file had no effect

SQLite is canonical. Export a review directory, edit that copy, and run cvkeharness memory import <directory>.

Import reports a secret marker

Remove the credential or sensitive parameter from the operational record. Store credentials in the system intended for secrets, not in CvkeHarness memory.

Import fails after an edit

Verify that every record references a known target, matches its environment, has a valid status and trust value, and has a future expiry when active. Active playbooks must have a success check. A validation rejection leaves SQLite unchanged. A view-write error after commit requires cvkeharness memory export to regenerate the views.

The state database is unavailable

Operational memory fails closed. Correct state_db_path or database access before using memory retrieval or mutation.

A reusable command approval does not match

Confirm the exact normalized command, action, target ID, environment, remote identity label, policy version, and expiry. An interactive approval also requires the exact session that created it; absent or different sessions fail closed. Explicit CLI policy exceptions are session-independent. One-off decisions, LLM judgments, and commands containing runtime interpolation are not reusable.

A deleted item is still present in a snapshot

Delete affects canonical operational state and generated current views. Existing snapshots are retained as audit history. The current CLI does not purge them.
